# 研究：Agentic 软件工程六大支柱与 Freely 架构

## Context

阅读了文章《Agentic 软件工程：造 Agent 只是最简单的部分》，作者 Ashpreet Bedi（Agno 创始人）。

核心观点：**造 Agent 是最简单的部分，让它在生产环境中稳定运行才是真挑战。**

文章提出了 Agentic 软件工程的六大支柱：
1. **持久性（Durability）** - 暂停、恢复、检查点
2. **隔离性（Isolation）** - 用户级隔离
3. **治理（Governance）** - 分层权限
4. **持久化存储（Persistence）** - 会话、知识存储
5. **规模化（Scale）** - 限流、延迟处理
6. **可组合性（Composability）** - API 调用、多 Agent 系统

### Freely 现状评估

| 支柱 | 当前状态 | 评估 |
|------|---------|------|
| 持久性 | 依赖进度文档恢复 | ⚠️ 部分支持，checkpoint 机制待完善 |
| 隔离性 | 单实例运行，无多用户 | ❌ 不支持 |
| 治理 | 依赖宪法约束 | ✅ 有基础治理框架 |
| 持久化 | 进度文档 + 项目文件 | ⚠️ 非结构化，需要改进 |
| 规模化 | 单实例 | ❌ 不支持 |
| 可组合性 | 无 | ❌ 不支持 |

### 与前一篇研究的关联

前一篇研究（20260303-agent-protocol-evolution）关注的是 **协议对齐**（MCP/ACP/A2A），侧重于 Agent 间的通信标准。

本文关注的是 **生产级运行**（六大支柱），侧重于让 Agent 稳定运行的基础设施。

**两者互补**：
- 协议对齐解决"Agent 如何对话"
- 六大支柱解决"Agent 如何稳定运行"

## Options

### Option A: 优先六大支柱

先解决生产级运行问题，再考虑协议对齐：

| 阶段 | 目标 | 支柱 |
|------|------|------|
| Phase 1 | 持久化存储升级 | Persistence |
| Phase 2 | 状态检查点机制 | Durability |
| Phase 3 | 治理框架增强 | Governance |
| Phase 4 | 可组合性准备 | Composability |

**优点**：
- 解决实际运行问题
- 渐进式提升稳定性

**缺点**：
- 与外部生态脱节
- 多 Agent 能力受限

### Option B: 优先协议对齐

先解决 Agent 通信问题，再解决运行问题：

- 与前一篇 Option B 一致

**优点**：
- 与生态逐步对齐
- 可复用外部成熟方案

**缺点**：
- 基础问题可能未解决

### Option C: 双轨并行

同时推进两项研究：

- 六大支柱：内部架构改进
- 协议对齐：外部生态对接

**优点**：
- 不互相阻塞
- 两条腿走路

**缺点**：
- 资源分散
- 可能需要更多决策

## Tradeoffs

### 复杂度对比

| 维度 | 六大支柱 | 协议对齐 |
|------|---------|---------|
| 理解难度 | 中等（软件工程经验） | 高（需理解多协议） |
| 实现难度 | 中等（数据库/状态管理） | 高（协议适配） |
| 依赖外部 | 低（自建） | 中（协议生态） |

### 实际价值评估

| 维度 | 六大支柱 | 协议对齐 |
|------|---------|---------|
| 短期价值 | 提升稳定性、可恢复性 | 暂无明确需求 |
| 长期价值 | 多用户、生产部署 | 生态互通 |

## Decision

**暂不决策** - 需要进一步验证：

1. Freely 当前的主要矛盾是稳定性还是生态互通？
2. 六大支柱中哪些是当前必须解决的？
3. 协议对齐是否需要等待六大支柱基础完成？
