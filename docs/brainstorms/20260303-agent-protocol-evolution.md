# 研究：协议对齐与架构演进方向

## Context

阅读了文章《2026 年，万物皆 Coding Agent 的平台工程新范式（A2A / ACP / MCP / Skill）》，结合 Freely 项目意图，探讨架构演进方向。

### 核心问题

Freely 本身就是一个 Agent 编排系统（外循环→内循环），与文章描述的趋势高度契合。但当前是单体架构，如何平滑演进以支持：

1. 协议标准化（MCP/ACP/A2A）
2. 能力外显（Skill/A2A AgentCard）
3. 可扩展执行层（外接 Coding Agent）

### Freely 现状

```
外循环(auto-loop)
├── Issue 发现与路由
│   ├── 项目意图 → 新需求
│   ├── review → 改进点
│   ├── test → Bug/修复
│   ├── 进度文档 → 未完成 Issue
│   └── Chat 输入/会话证据 → pre-brainstorms 候选收敛
│
└── 路由到内循环
    ├── D:doc-loop (IBM)
    │   ├── I (Intake)
    │   ├── B (Brainstorm)
    │   └── M (Map)
    │
    └── D:dev-loop (DDD)
        ├── doc → 阅读文档
        ├── dev → 开发
        └── doc → 更新文档
```

## Options

### Option A: 保持单体架构

继续在单体架构内演进，通过模块化设计支持：

- 内部抽象出 Router、Loop、Executor 等模块
- 不引入外部协议，仅内部使用

**优点**：
- 简单可控
- 渐进式演进风险低

**缺点**：
- 无法与外部 Agent 生态互通
- 能力无法被其他系统调用

### Option B: 渐进式协议对齐

分阶段引入协议支持：

| 阶段 | 目标 | 协议 |
|------|------|------|
| Phase 1 | 能力封装为 MCP Server | MCP |
| Phase 2 | 支持外接 Coding Agent | ACP |
| Phase 3 | 跨平台协作 | A2A |

**优点**：
- 平滑演进
- 每阶段可验证
- 与生态逐步对齐

**缺点**：
- 需要维护多套接口
- 协议升级可能带来适配成本

### Option C: 全量协议对齐

一次性引入 A2A + MCP + ACP：

- 完整的 Agent Card 暴露
- 标准化工具接口
- 外接多个 Coding Agent

**优点**：
- 一步到位，与生态完全对齐
- 面向未来

**缺点**：
- 改动大，风险高
- 可能过度设计
- 需要理解协议细节

## Tradeoffs

### 技术复杂度

- 单体 → 协议化：复杂度显著提升
- 需要理解 MCP/ACP/A2A 协议细节
- 需要处理协议版本演进

### 团队能力要求

- 需要协议适配开发经验
- 需要多 Agent 调试能力
- 需要状态一致性处理经验

### 实际收益评估

| 收益 | 评估 |
|------|------|
| 与生态互通 | 长期有价值，短期场景未知 |
| 能力复用 | MCP Server 可被其他 Agent 调用 |
| 执行层扩展 | 可接入 Claude Code 等提升编码能力 |

## Decision

**暂不决策** - 需要进一步验证：

1. **需求验证**：当前 Freely 的实际使用场景是否需要协议互通？
2. **成本评估**：实现各阶段协议需要多少工作量？
3. **优先级排序**：协议对齐 vs 其他功能演进哪个更优先？
