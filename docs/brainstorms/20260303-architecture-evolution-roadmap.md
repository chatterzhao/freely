# 研究整合：Freely 架构演进路线图（协议对齐 + 生产级能力）

## 目标

避免 `20260303-agent-protocol-evolution` 与 `20260303-agentic-software-engineering` 相互覆盖，保留两者独有价值，并形成可执行的统一路线图。

## 评审结论（保留策略）

1. 保留 `20260303-agent-protocol-evolution.md`：它定义了对外互通能力（MCP/ACP/A2A）和协议分阶段路径。
2. 保留 `20260303-agentic-software-engineering.md`：它定义了生产可运行性（六大支柱）和稳定性优先的工程视角。
3. 本文档作为主版本：后续讨论与执行以本文档为准，前两篇作为来源材料，不做“后文覆盖前文”。

## 统一问题定义

Freely 当前不是“只缺协议”或“只缺稳定性”，而是存在两个正交目标：

- 目标 A（内部）：提升可恢复、可治理、可扩展的生产运行能力。
- 目标 B（外部）：建立与 Agent 生态的协议互通能力。

结论：采用双轨架构，但阶段不平均分配资源，先夯实最小运行底座，再逐步开放协议边界。

## 双轨路线（带门槛）

### Track A：生产级能力（优先级更高）

Phase A1（立即）：
- 结构化状态持久化（替代纯文档恢复）
- 最小检查点机制（可暂停/恢复）
- 审计日志与治理动作落盘（谁在何时做了什么）

Phase A2：
- 会话/任务隔离模型（为多实例并发做准备）
- 限流与重试策略（避免循环雪崩）

Phase A3：
- 可组合执行接口（为协议化适配做内部抽象）

### Track B：协议对齐（分阶段接入）

前置条件：
- A1 完成后启动，避免“接口已开放但内部不稳定”。

Phase B1：
- MCP Server PoC（只暴露低风险能力）

Phase B2：
- ACP 适配执行层（外接 Coding Agent）

Phase B3：
- A2A 协作与 Agent Card（跨平台协同）

## 关键决策

1. 采用“双轨并行 + 门槛控制”，不是二选一。
2. 资源分配建议：近期 `Track A : Track B = 7 : 3`。
3. 协议能力按“最小可用接口”开放，避免一次性全量协议化。

## 与项目意图/宪法对齐

- 对齐项目意图的“持续自主循环”：A 轨优先保障循环稳定与恢复连续性。
- 对齐宪法的“恢复强制性与可追溯”：A1 的检查点和结构化状态是直接支撑。
- 对齐长期生态目标：B 轨确保后续可接入外部 Agent 生态，而非封闭单体。
