## Research Questions And Current Judgement

### 1. Which runtime evidence fields should be structured vs flexible?

Current judgement:

- Structured:
  - `cwd`
  - resolved entrypoint path
  - target project root
  - invocation mode (`direct`, `patched`, or equivalent canonical enum)
  - source artifact class for the item being judged (`manager_continuity`, `worker_prompt`, `delegated_intake`, `followthrough`, or equivalent bounded class)
  - source artifact pointer for the prompt/continuity/intake being absorbed
- Flexible:
  - adjacent freeform diagnostic snippets
  - tool-native stderr/stdout excerpts
  - optional environment-specific annotations

Benefits:

- Makes absorption and recovery decisions auditable instead of string-matching freeform logs.
- Lets runtime/status surfaces distinguish "same workcell, same target, different invocation provenance" from generic failures.

Harms:

- More fields increase writeback noise and schema-maintenance cost.
- Over-freezing fields too early risks encoding tool-specific quirks as canonical runtime truth.

Boundaries:

- The goal is not a universal telemetry schema for every runtime event.
- The minimum freeze should only cover fields needed to judge provenance, absorption, and replay safety.

Counterexamples:

- A one-off tool stderr blob or vendor-specific websocket trace should remain flexible evidence, not a required structured field.
- Feature-local verification artifacts may not need the same runtime provenance schema as control-plane continuity.

Why looser behavior can still be better:

- Early research and environment-specific failures benefit from cheap freeform capture before a stable contract exists.
- Over-structuring pre-IBM evidence would slow discovery loops without improving current decisions.

### 2. Where should the canonical absorption gate live, and how do we avoid false positives against legitimate feature-owned verification?

Current judgement:

- The gate should live at the control-plane absorption boundary, not inside generic feature verification or inside every issue's own verification artifact.
- It should consume:
  - authoritative source artifact identity
  - source artifact class
  - owner/phase compatibility
  - provenance sufficiency
  - same-lane supersession rules
- It should explicitly exempt legitimate feature-owned verification evidence when that evidence is bounded to an existing issue and is not trying to rewrite manager/control-plane truth.

Benefits:

- Keeps manager/runtime absorption decisions centralized and auditable.
- Prevents feature verification from being mistaken for control-plane ownership transfer.

Harms:

- A centralized gate can become noisy if it inspects artifacts that were never intended to participate in control-plane absorption.
- Too much strictness can delay legitimate followthrough and create docs-only churn.

Boundaries:

- The gate should judge canonical absorption into runtime/continuity/control-plane truth, not every form of artifact publication.
- It should not override issue-level verification closeout for bounded feature owners.

Counterexamples:

- A feature issue writing a verification artifact under its own `verification_artifact_dir` should not fail merely because it lacks manager-only continuity fields.
- A review note proving local implementation correctness is not itself a manager absorption attempt.

Why looser behavior can still be better:

- Some lanes need fast local verification before deciding whether manager/runtime absorption is even relevant.
- Loose routing preserves supervisor flexibility while the exact gate inputs are still unsettled.

### 3. Does manager continuity materialization need a stronger contract or fallback?

Current judgement:

- Yes, but only around the minimum evidence needed when continuity cannot cleanly materialize or when a candidate artifact is ambiguous.
- The stronger contract should prefer:
  - explicit "why not materialized" truth
  - provenance to the attempted source artifact
  - next recovery gate / revisit trigger
- Fallback should remain manager/control-plane-only and should not be required for successful continuity refreshes, ordinary feature verification, or transient waits that have not yet crossed a blocked or ambiguous boundary.
- It should avoid turning every transient writeback hiccup into a new heavy artifact family.

Benefits:

- Reduces false-active states where prompts advance but authoritative continuity never does.
- Gives runtime and later workers a smaller, clearer recovery surface.

Harms:

- More fallback artifacts can increase noise and create parallel truth if the main continuity artifact eventually lands anyway.
- Operators may start treating fallback artifacts as equivalent to successful continuity materialization when they are not.

Boundaries:

- Fallback should exist only when canonical continuity truth cannot safely be produced.
- It should remain a bridge artifact, not a replacement for normal continuity on healthy paths.

Counterexamples:

- A brief launch delay or expected same-lane busy wait should not force a fallback artifact.
- A fully successful continuity writeback should not also emit a redundant fallback record.

Why looser behavior can still be better:

- Current lighter behavior minimizes write amplification on fast-moving manager rounds.
- Supervisor judgement sometimes needs room to defer materialization until more evidence arrives.

### 4. Should same-lane authoritative prompt replacement be tightened?

Current judgement:

- It likely should be tightened for cases where a new artifact claims to supersede same-lane truth, but the tightening must stop short of removing supervisor discretion for lawful same-lane waiting, freeze, or bounded followthrough.
- The narrowest useful rule is:
  - supersede only when the new artifact targets the same lane and owner surface
  - carries equal-or-stronger provenance than the current authoritative artifact
  - and explicitly declares replacement intent rather than merely attaching supporting evidence

Benefits:

- Prevents stale or weakly-proven prompts from silently replacing stronger same-lane authority.
- Reduces ambiguity when multiple same-lane artifacts exist with different provenance quality.

Harms:

- Too-tight supersession rules can block legitimate supervisor interventions.
- Same-lane rounds sometimes need to preserve partial context instead of hard-replacing earlier prompts.

Boundaries:

- Tightening should apply to authoritative replacement, not every advisory or supporting artifact.
- Replacement logic must distinguish supersession from "coexist as evidence" and from "feature-local verification only".

Counterexamples:

- A same-lane note that only adds supporting diagnostics should not have to replace the current authoritative prompt.
- A manager may need to keep an older continuity authoritative while attaching a narrower follow-up prompt as supporting evidence.

Why looser behavior can still be better:

- Looser replacement keeps supervisor flexibility during ambiguous investigations.
- In research-heavy rounds, hard supersession can prematurely erase useful context provenance.

  - source artifact identity is concrete and canonical

- Fallback is justified only when:
  - canonical continuity cannot safely materialize
  - or the candidate source artifact is ambiguous enough that absorbing it would be unsafe
- Fallback must record:
  - why continuity was not materialized
  - which source artifact was attempted
  - which next recovery gate or revisit trigger remains
- Fallback must not be emitted for:
  - healthy same-lane continuity refresh
  - lawful same-lane busy wait
  - ordinary issue-bound feature verification
