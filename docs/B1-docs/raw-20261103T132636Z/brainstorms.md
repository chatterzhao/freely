## scope 收敛

本轮做 1 + 4，理由：

- 两者都是**单点、可静态验证、后果最直接**（RCE / 评审通过后流程中止）。
- 2 与 3 都要改数据格式与读侧协议（状态文件格式、派发通道），各自需要迁移与兼容期，混在一个 PR 里无法独立验证「行为不变」。
- 4 的一条额外发现（`wt-close` 的 `.bak` 残留）证明「混用两种 `sed -i` 语法」本身就是缺陷面。

## 方案方向

### 面 1：heredoc + argv

- 不能继续用 `python3 -c "..."`：只要有任何外部值进入脚本体，就必须做引用转义，而转义做对的前提是「知道值里有什么」——外部输入不满足。
- 改用 `python3 - "$ROOT_DIR" "$review_branch" <<'PY'`，脚本体是**静态文本**（`<<'PY'` 不做任何展开），值走 `sys.argv`。
- 这样注入面从「任意字符串」降到「argv 元素」，python 不解析 argv。

### 面 4：`sed -i.bak` + 同命令清理

- `sed -i ''` = BSD 语法；GNU sed 把 `''` 当文件名，退出非零。
- `sed -i.bak` 两种平台都合法：BSD 自动删 `-i` 参数的备份名？不——BSD 用 `-i.bak` 同样生成 `.bak`，GNU 也是。差异消失。
- 代价是多一个 `.bak` 文件，必须**同命令**删除，否则残留会污染工作树（`wt-close:1251` 的既有 bug）。
- 不用 python 替代 `sed`：改动面更大，且 `sed` 在这里只做单行文本替换，没有跨行需求。

## fidelity 基线

- 注入必须用**真的会执行**的 PoC 证明：`python3 -c "print('fix/x');print('PWNED');#')"` 输出 PWNED —— 若 PoC 不执行，说明测试本身没测到点。
- 安全侧断言 argv 形式**原样**收到 payload 且无额外输出。
- `sed` 必须验证「文件被改写」+「无 `.bak` 残留」两个条件。

- 不重叠：#4246（已建的输入边界二）承接状态文件/TSV/剩余 `python3 -c`；#4239 是并发，无关。

## 被否决

- **一次性改完 195 处 `python3 -c`**：每处都要判断「是否真有外部值进入」，机械替换会破坏需要插值的合法场景；应先加 lint 再收敛。
- **用 `printf %q` 转义后仍走 `python3 -c`**：转义正确性依赖 bash 版本与平台，且 `%q` 对 python 字符串字面量不是同一套规则。
- **`sed -i.bak` 但把清理放到函数退出时**：中间失败会残留，且并发调用会互相删错。
- **本轮顺带做状态文件/TSV**：需要协议迁移，无法与「行为不变」一起验证。
