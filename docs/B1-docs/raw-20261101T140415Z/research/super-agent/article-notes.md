# 文章逐节笔记（事实层）

> 只记录文章说了什么、为什么、边界与假设；Freely 的判断放到 `intent-map.md` / `decisions.md`。

## 1. Super-agent：四个特征

**问题**：单 Session Agent 的多任务上限不是模型能力，而是人的注意力。一个人通常只能同时跟进 3–5 个活跃 Session；多任务要手动切换、记上下文；本地设备离线就停。

**主张**：把 Agent 与“一次手动 Session”解绑，变成能跨会话保持上下文、同时推进多项复杂任务且互不干扰的连续实体。

**四个特征**：

- 连续：IM/GitHub 等界面里像同一个 Agent；方案 A→B 的跨信道变更能接住。
- 高效：无需等上一条命令完成就能接新指令；多任务并行。
- 主动：持续观察环境事件，无需逐条指令；不需要时保持安静。
- 持久：始终在线、接入真实工作环境、异常自愈。

**关键判断**：单个 ReAct Loop 无法同时支持四个特征，所以需要系统架构，而不是更大的 prompt。

**五个模块**：

1. 双层架构（连续交互 + 并发）
2. 事件驱动（主动）
3. 面向人的交互（连续 + 高效）
4. 计算/状态/环境分离（持久）
5. Watchdog（持久 + 自愈）

## 2. 双层架构

**根本 trade-off**：所有事件一个 Session → 上下文最连续，但单 ReAct Loop 串行、吞吐低、任务混杂；每个事件新 Session → 并发最高，但缺全局上下文、多 Session 回复混乱。

**解法**：把“维护全局连续性”和“高并发执行”拆成两层。

### 2.1 Router 层

- 常驻全局路由层，承接所有入口的人类交互；是全局序点、协调点、记忆。
- 不直接执行具体任务，只做人类交互与任务分派；甚至可以不配 Bash。
- 与常见 Agent Team 的区别：Team Lead 深入子任务、重推理；Router 只处理任务间高层关联，不介入单任务内部拆解。
- 实现：单个常驻 LLM Session；上一轮推理期间到达的事件积压，下一轮合并批处理。
- 批处理效果：事件平稳时逐条低延迟；拥堵时合并，Prefill 并行，单次耗时增长慢于 batch，单决定分摊时间下降；上限是上下文长度和单轮可准确处理的 Trigger 数。
- 扩展：规模更大时可多层过滤/水平分片，但分片越细，跨片连续性越低；全局记忆未解决前 trade-off 一直在。

### 2.2 Worker 层

- 每个 Worker 上下文隔离，挂完整执行工具，专注单一任务；通常配最强模型。
- Worker 不直接与人类交互；推理/工具调用不直接输出外部信道；向 Router 汇报，由 Router 统一回复。
- Worker 间通常不直接通信；共享工作环境（同一 PR）的冲突通过订阅同一 Thread 收到相同事件，自行发现/解决；少数跨任务协同由 Router 中转。
- Worker 内部可再建 Subagent/Agent Team，对 Router 透明。
- 适用于代码协作，也适用于个人助手：前端一个聊天页，底层按话题分 Worker。

## 3. 事件驱动

**驱动方式变化**：主要输入不再是人类逐条 prompt，而是环境半结构化事件（Trigger）：群聊、邮件/日程、代码评审评论、CI 结果等。

### 3.1 事件过滤（Fast/Slow Path）

- 现实事件流“高噪音、低触发率”；每个事件都调 LLM 成本和延迟不可接受。
- 程序层 Fast Path：来源、群组范围、用户/机器人白名单等确定性条件；按来源设“仅明确请求 / 候选 / 忽略”。
- 语义层 Slow Path：通过程序准入的候选交给 LLM，按 prompt 策略和上下文判断是否行动；也是自然语言策略扩展点。
- 示例：闲聊被程序层拦截；用户群日常消息放行但语义层静默；具体缺陷反馈触发路由。

### 3.2 事件路由（Thread / Subscription / 直通）

- 同一 PR、同一 IM 话题、同一邮件串下的连续事件构成 Thread。
- Router 根据 Thread 初始事件创建 Worker 后，Worker 直接订阅 Thread。
- 已订阅（Fast Path）：后续事件程序直通 Worker，不经 Router；Worker 可退订/交回。
- 未订阅（Slow Path）：Router 仍可观察所有事件，但只判断/分派尚未订阅的新事件。
- Thread 与 Worker 订阅多对多：一个 Worker 可订阅多个 Thread；一个 Thread 可被多个 Worker 订阅；共享环境中的冲突通过同一事件通知暴露。
- 输出侧：Worker 关键结论仍汇报 Router，由 Router 统一回复、同步全局记忆。

### 3.3 上下文组织（Inline & Spill / Chain of Recall）

- 上下文窗口当 Cache 管理。
- Inline：近期高概率用到的信息直接内联，省工具往返。
- Spill：超预算/低频信息留在窗口外，只留引用/摘要，按需读取。
- 渐进策略：先给对象 ID + 摘要；利用局部性内联紧密关联对象 ID、时空相邻内容（前 50 字、前后消息、相邻评审评论）；超上限截断并留续读入口。
- 链式召回：Trigger/Thread/Worker 等对象有唯一 ID，注入时内联下一跳 ID，构成引用图；每次召回结果同样 Inline & Spill，模型可逐跳展开。解决 Router 长程丢上下文。

### 3.4 提前行动（Speculative Execution）

- 在不确定结果是否被采用时，根据环境信号后台提前尝试；有价值交付，无价值丢弃。
- 个人助手：会议邀约→后台查冲突/背景/草稿。
- 研发：群内反馈/讨论改动→后台复现并找简单修复；确认后才交付，否则静默。
- 示例：讨论还没结束，已提交修复 PR。

## 4. 面向人的交互

### 4.1 全双工：异步 ReAct Loop

- 经典 ReAct Loop：模型发起同步 `run()` 工具调用后阻塞，直到工具完成；会话无法响应新输入（半双工）。
- 异步 ReAct Loop：耗时命令/子任务改为 `start()` / `stop()`；`start()` 立即返回 Started；后台执行完成后把结果作为新事件投递进会话；模型可 `stop()` 终止过长后台命令。
- 效果：前台响应与后台执行解耦；后台跑耗时任务时仍能响应人类输入；新输入在当前推理步结束后处理，不必等后台工具完成。
- 重要事实：文章说异步任务机制**已在 DeepSeek Harness 实现，但尚未默认开启**。

### 4.2 多信道交互

- Worker 的冗长推理/密集工具调用隔离在内部，不直接输出外部信道；Router 统一对外。
- IM：低打扰、像同事；只在需要决策/验收时通知；只问直接问题、给简短结论；硬规定单次回复 ≤100 词。
- GitHub/邮件/文档：结构化、高信息密度；PR 写完整背景/改动/验证；邮件/文档给结构化摘要。

## 5. 计算、状态与执行环境分离

现状问题：本地 Agent 把 Agent Loop、会话状态、执行环境绑在同一台设备；休眠/离线就停，无法访问其他设备环境。

### 5.1 计算与状态分离

- Agent Loop 计算可无状态；持久的是 Session 状态。
- 计算放云端无状态弹性容器；Session 等状态存数据库；容器可水平扩展/重启/替换；连续性由持久化存储保障。

### 5.2 计算与执行环境分离

- 复制/同步真实环境很难：未提交修改、私有凭据、内网服务、硬件/工具链；要求用户迁云端成本高。
- 让 Agent Loop 在云端，重状态执行环境留在原地；端侧只放不保存会话状态的轻量 daemon，负责执行命令/返回结果。
- 与 Anthropic “脑手分离”一致；区别是这里首先接入用户日常、可能间歇在线的个人机器（BYOM），也支持云端托管/按需环境。
- 可跨设备切换；设备重新上线后云端 Agent 可触发完成需要该设备的任务。

## 6. Watchdog

- 持久在线不能只靠主系统内部逻辑；需要主系统之外的独立 Control Loop。
- 仅进程存活/监控脚本不够：异常可能是模型无效循环/偏离目标。
- 做法：主系统外独立 Watchdog Session，定时消息驱动；既处理接口报错/状态恢复失败，也由模型判断 Worker 是否有实质进展/方向偏离；发现异常介入修复，偶发故障持续复查。
- Watchdog 本身是完整工具能力的 Agent Session；维护者可用自然语言问故障原因，也可让它在线修正主系统行为（提示词、触发规则）。

## 7. 初步实验

### 7.1 消融

- 负载：群聊 + GitHub CI 消息流；约 300 条消息/次，其中约 20 条工作请求；其余闲聊、跟进、叫停、CI；编码工作用只消耗时间的工具代替；每种方案 5 次。
- 四方案：Super-agent；去掉直通的 Super-agent；单 Session + Subagent（中性提示）；单 Session + Subagent（提示优先委派）。
- 结果：
  - Super-agent p50 12.4 min / p95 15.7 min。
  - 单 Session + Subagent 中性 p50 20.4 / p95 29.5；5 次中一次都没调用 Subagent。
  - 提示优先委派 p50 13.8 / p95 29.0；5 次中 4 次委派，仍有 1 次自己执行形成长尾。
  - 去掉直通：p50 12.6 / p95 15.5，完成时间基本不变；Router 决定数 +30%，读缓存 token 2323 万→3177 万（+37%）。
- 解释：直通不提升完成质量/速度，但省 Router token/推理；双层架构用系统约束替代提示词工程的分工不确定性。

### 7.2 Router 批处理

- Trigger 到达率 ~1→40 条/分钟；平均 batch 1.0→2.8；单次请求耗时 2.5→3.9 s；单决定分摊 6.4→1.6 s。
- 结论：拥堵时自动合并提高有效吞吐；当前团队规模无需水平切分 Router。

### 7.3 实验边界

- 合成负载、简化环境；工作用耗时工具替代，不衡量单任务执行质量。
- 1/4 缩放消息间隔/工作时长；模型调用耗时为真实值。
- 单一团队/仓库/场景；不能直接外推到多项目、多租户、长程记忆。

## 8. 开放问题

1. 双层扩展：Router 何时水平切分/粒度；Worker 间何时直接通信/拓扑；长程记忆跨月；模型与系统 co-design。
2. 脱离 Session 的产品形态：聊天窗口是路径依赖；领域特化界面（GitHub Issue/PR）；用户看到的一个会话底层未必一个 Session；中途介入/接管/实时协同仍需探索。
3. A2A：组织内/组织间多实例的上下文边界；不共享上下文、不同权限边界下如何安全可靠协作。
4. 安全隐私：云端 Agent 接入外部事件 + 端侧私有代码/凭据；云端被入侵/提示注入会控制所有端侧设备；凭据不应进入模型上下文但仍需使用。

## 9. 结语与示例项目

- 没有全新理论；把计算机系统经典工程思想用于 Agent 系统。
- 五个模块：双层、事件驱动、异步多信道、存算分离、外部 Watchdog。
- 内部 Super-agent 已持续运行，参与问题复现/修复、代码审查响应、DSH 自身迭代。
- 示例项目 `dsh-superagent-prototype` 是实现部分设计的 research prototype，不是正式产品；文章部分设计是未来方向，原型未必实现。
