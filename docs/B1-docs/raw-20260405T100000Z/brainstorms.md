# 预研头脑风暴：CLI Output Conciseness and Token Efficiency

## 背景

用户观察到：网上有人说使用文言文可以省 token，特别是终端界面的陈述过程。用户提出提示词方向：

> 汝以文言作答。凡回复，惜字如金，不赘不饰。先行后言，果先因后。若无必要，勿增实体。

这个问题需要验证：
1. 文言文是否真的省 token？
2. 如果省，是否值得牺牲用户接受度？
3. 是否有更实用的精炼风格？

## 已确认事实

### 1. Token 效率取决于 tokenizer，不是字数

- Token 数量由模型的 tokenizer 决定
- 中文 token 化通常是字符级别或子词级别
- "吾已完成" vs "我已经完成了"
  - 文言文：4字 → 可能 4-5 tokens
  - 白话文：7字 → 可能 7-8 tokens
- 节省有限，但存在

### 2. 文言文的隐藏成本

- **上下文理解成本**：需要更多推理 token 来理解文言文
- **信息完整性**：过度精简可能丢失关键信息
- **用户接受度**：不是所有用户都习惯文言文
- **编程场景**：代码、路径、命令需要精确，不适合文言文

### 3. 核心思想可以保留

用户提出的核心思想有价值：
- 精炼表达
- 先行动再汇报
- 结果导向
- 奥卡姆剃刀原则

这些思想可以用白话文实现，不一定需要文言文。

## 初步边界判断

问题不是"是否使用文言文"，而是：

1. CLI 回复风格如何约束？
2. 约束范围如何界定？
3. 如何平衡 token 效率与信息完整性？

## 候选方向

### 方向 A：文言文约束

优点：
- 有特色
- 可能省少量 token

缺点：
- 理解成本高
- 用户接受度不一
- 编程场景不适用

### 方向 B：CLI 精炼风格（推荐）

采用"CLI 精炼风格"而非文言文：

```markdown
# CLI Output Style

When outputting to CLI:
1. Be concise. No filler words.
2. Result first, explanation after if needed.
3. Use lists and code blocks over prose.
4. Skip conversational openers.
5. For programming tasks: code speaks louder than words.
```

优点：
- 通用、实用
- 不牺牲可读性
- 编程场景友好

缺点：
- 无特色

### 方向 C：混合模式

- 默认精炼风格
- 用户可选文言模式

缺点：
- 复杂度高
- 维护成本高

## 当前判断

倾向方向 B。

原因：
1. Token 节省的本质是精炼，不是文言文
2. 精炼风格更通用，用户接受度更高
3. 编程场景不需要文言文

## 本轮决策

1. 这次先视为开发 Freely 过程中的入口实验，不视为 Freely 能力发现。
2. 产物暂时只落到 `AGENTS.md`。
3. 风格采用“精炼白话文”，不采用文言文。
4. 约束范围仅限开发 Freely 过程中的人类可读 CLI 输出与 chat 回答，不扩展到 runtime / skill / CLI 能力真源。
5. 这轮讨论同时确认了一条已存在的 Freely 能力事实：Freely 当前已经会在项目初始化时补最小 `AGENTS.md`，并在执行前优先读取项目级 `AGENTS.md`；Freely 自举时同样遵循这个项目级入口契约。

## 后续重开条件

1. 现有 `AGENTS.md` 约束仍无法明显改善输出质量。
2. 需要把这套风格约束推广为 Freely 对外长期消费的能力定义。
3. 需要用更高优先级真源重新冻结“回复风格属于产品架构还是能力目录”的边界。
