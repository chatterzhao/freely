# 研究：Freely CLI 编排架构与外部工具接入策略

## Context

### 设计决策核心

**核心架构思路**：
1. **CLI 编排为主**：通过命令行调用外部工具
2. **无交互自动批准**：自动化流程，无需人工介入
3. **进程重启持久运行**：会话恢复、会话压缩、新会话机制
4. **外部工具复用**：不自己开发，充分利用现有 CLI 工具

### 约束与哲学

- **外部工具 = 宪章 API**：所有外部 CLI 工具视为"外部 API"，必须遵守宪法约束
- **传入式约束**：每次启动外部工具时，传入"宪章"或"品味.md"作为行为约束
- **类似 Skill 机制**：参考 A2A Skill 概念，但通过传入配置文件实现

## 二、外部工具接入策略

### 2.1 必须自己开发的能力

| 能力 | 理由 | 当前状态 |
|------|------|---------|
| Issue 管理 | 核心闭环，必须自己掌控 | 需开发 |
| 文档驱动 | 项目意图、宪法落地 | 需开发 |
| 流程编排 | auto-loop 逻辑 | 需开发 |
| 会话管理 | 恢复、压缩、新会话 | 需开发 |
| 质量门禁 | 验收标准、测试围栏 | 需开发 |

### 2.2 可接入的外部工具

| 工具类型 | 接入方式 | 约束机制 |
|----------|----------|----------|
| Claude Code | CLI 调用 | 传入品味.md |
| OpenCode | CLI 调用 | 传入品味.md |
| Git CLI | 原生 | 遵守分支规则 |
| 代码审查工具 | CLI 调用 | 传入验收标准 |
| 测试框架 | CLI 调用 | 传入测试规范 |

### 2.3 传入式约束机制

```bash
# 方式 1：环境变量
TASTE_FILE=/path/to/taste.md claude --prompt "..."

# 方式 2：配置文件
# 在外部工具配置目录放置品味.md

# 方式 3：命令行参数
opencode --taste=/path/to/taste.md --task=xxx
```

**品味.md 示例结构**：
```markdown
# 品味.md

## 核心约束
- 必须遵守项目宪法
- 遵循项目分支规则

## 开发规范
- 使用 TypeScript strict mode
- 测试覆盖率 > 80%

## 验收标准
- 集成测试通过
- 无 lint 错误
```

## 三、会话持久化机制

### 3.1 会话恢复

```
运行中崩溃
    ↓
检查点保存（进度文档）
    ↓
重新启动 → 读取检查点
    ↓
从断点继续
```

### 3.2 会话压缩

```
长会话上下文
    ↓
提取关键状态：Issue 进度、文档版本、执行位置
    ↓
压缩为精简上下文
    ↓
新会话启动
```

### 3.3 新会话

```
无法恢复
    ↓
基于进度文档重建上下文
    ↓
生成新的会话
    ↓
继续执行
```

## 四、验收标准先行

### 4.1 核心理念

**先定义验收，再开始实现**

```
Issue → 验收标准 → 集成测试 → 实现 → 验收通过 → 完成
```

### 4.2 实施方式

1. **Story 阶段**：明确验收项（Given/When/Then）
2. **实现前**：先写集成测试（测试门禁）
3. **实现后**：测试通过即完成

### 4.3 与外部工具对接

```bash
# 调用外部编码工具前，先确保测试存在
if ! test -f integration_tests/$issue_id.test.sh; then
    echo "Error: 验收测试不存在"
    exit 1
fi

# 传入验收标准
claude --taste=taste.md --task="实现 $issue_id，验收标准: $acceptance_criteria"
```

## 五、集成测试重点推进

### 5.1 为什么是集成测试

| 测试类型 | 适用场景 | 与 Freely 关系 |
|----------|----------|----------------|
| 单元测试 | 单函数验证 | 外部工具负责 |
| 集成测试 | 多组件协作 | Freely 把控 |
| E2E 测试 | 完整流程 | 验证闭环 |

**结论**：Freely 负责集成测试，因为这是项目级闭环的核心

### 5.2 集成测试门禁

```bash
# 每个 Issue 必须有对应集成测试
# 测试位置：tests/integration/$issue_id.sh

# 门禁规则
- 无测试 → 不得合入 main
- 测试失败 → 阻塞推进
- 测试通过 → 自动放行
```

## 六、与前期研究的整合

### 6.1 六大支柱对应

| 支柱 | Freely 实现方式 |
|------|----------------|
| 持久性 | 会话恢复/压缩/新会话机制 |
| 隔离性 | 通过进程隔离实现 |
| 治理 | 宪法 + 品味.md 约束 |
| 持久化 | 进度文档 + 项目文件 |
| 规模化 | 进程级扩展 |
| 可组合性 | CLI 接入外部工具 |

### 6.2 协议对齐位置

| 协议 | 在 CLI 架构中的角色 |
|------|---------------------|
| MCP | 可选：作为外部工具接入标准 |
| ACP | 可选：管理外部编码 Agent |
| A2A | 暂不优先：当前 CLI 模式足够 |

**结论**：协议对齐是"锦上添花"，当前 CLI 编排模式已满足需求

### 6.3 Skill 机制映射

| A2A Skill | Freely 实现 |
|-----------|-------------|
| Skill 定义 | 品味.md |
| Skill Matcher | Issue Router |
| Skill 触发 | auto-loop 调度 |
