## 方案评估

1. **为什么新增纯模块而不是把函数塞进 adapter**：`issue-sync._platform_title()` 会在 `sync` 中遍历数百个 issue 时被调用；subprocess 加载整个 adapter（含 handler 注册）开销大，且 bash 侧无法单测。纯 stdlib 模块可直接 import，也可被 adapter 同目录 import，是最小公共依赖。
2. **为什么保留旧的宽松标题判定**：原判定 `f"raw-{raw_key}" in title or f"RAW-{raw_key}" in title` 对历史 issue 的 loose 身份声明兼容；收紧为「必须 canonical 前缀」会让大量历史标题触发不必要的平台写回。因此新增的 `is_canonical_raw_title()` 是**补充**而非替换。
3. **为什么平台修正要遍历所有 replica**：原实现只取 `next(iter(replicas))` 的第一个平台，双平台会长期不一致；`raw-reconciliation-gate` 随后判 `content_diverged`。遍历修正可让两侧 fingerprint 一致。
4. **为什么 `issue-sync create` 失败只告警不阻断**：`cmd_create` 对已存在的平台副本会走 dedup 分支；在部分配置缺失（如无 GITEE_TOKEN）时返回非 0 是既有行为。直接让 pull 失败会把「标题未归一化」升级成「无法开工位」，超出本 issue 边界。告警即可让上层诊断。
5. **为什么 `feedback edit` 不回写历史**：只在 `has_title` 且 `kind == raw` 时对用户显式传入的 title 做规范化，不做任何扫描或批量 update；历史 issue 标题保持原样，符合 raw issue 修复方案 5 的评估要求。
6. **H1 边界**：物化 body 缺一级标题属 Q3；本 PR 不修，只在 B1 issue.md 现场补回 H1。否则 `issue-sync._platform_title()` 会 fallback 到 `local_id` 生成 `[RAW-key] raw-key`，把刚修正的标题改坏。
