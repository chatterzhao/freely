## 为何用「平台侧发现」而非「补 pull」
合同问题在 `cmd_create`/`cmd_close` 本身把本地缓存当事实。`raw-issue-pull` 的 create-backfill 只是触发链之一；直接运行 `issue-sync create`、wt-create 恢复、手动调用都能触发。修 create 自身的身份判定是根，pull 减噪是可选优化（本轮不夹带，证伪见 B1 brainstorms）。

## 为何引入纯模块 `replica_guard.py`
身份判定（receipt.status → present/absent/indeterminate）是可穷举的纯逻辑，与 I/O 分离后可单测 8 形态（含 malformed / ok-no-id / 平台缺失），且遵守 R1「评审证伪：不要改搜索层」——真实 `discover_raw_replicas` 与 reconciliation-gate 共用同一解析器，判定模块只读不写。与 Q1 pretests-gate `_field_line_value`、Q2 `raw_title_contract.py`、R1 `governance_repo_view.py` 同构：纯真源 + 薄 I/O 边界。

## 三态而非二态（关键：失败关闭）
- `present`：平台确认唯一 canonical 副本（status ok + issue_id）→ 回填，绝不建。
- `absent`：平台确认 not found（status missing）→ 唯一允许建单的状态。
- `indeterminate`：unknown / ambiguous / 平台缺失 / 畸形 / ok 无 id → 一律「不确定」。R7(#4195) 原则「读失败不是事实」：不确定时绝不建单（建了就可能重复），也不认证 platform_state 成功。ambiguous 尤其不能建——再建会加剧重复。

## 健康路径零退化
guard 只在「某配置平台本地缺 id」时才调 `discover-raw`；缓存完整时 `_missing=0` → 不查、不建、不改写。这既避免每次 create 都加一个平台往返，也让健康路径与 develop 逐字节一致（行为测试 `behavior_healthy_path` 断言 discover-raw 零调用、零建单）。

## close 侧：只补缓存不动 close_platforms 真源
strict `cmd_close` 在 `_raw_effect close-platforms` 之前调 `_backfill_close_replicas`，把平台 present 的缺失 id 回填进 `platform_ids`；`close_platforms` 照旧用它组 close-multi，于是覆盖全部真实副本。不改 R12 的四段式/退出码。加「终态守卫」：非 absorbed/dropped 直接 return，保 R12「非终态 raw 关闭零写入」不变量（`behavior_close_nonterminal_no_write` 断言 doc 逐字节不变）。

## 残余风险
- `raw-issue-pull` 仍在 partial(rc3) 时调 create，但此时 create 已幂等/失败关闭，不再重复；顺带减噪留待 #4166 入口收敛或 `issue-sync reconcile`。
- 真机「平台降级→恢复」的端到端建单未跑（不制造真实抖动）；以隔离 mock 的固定 receipt 矩阵 + 真机 read-only `discover-raw` 组合覆盖（验收标准明确「隔离 mock server 验证」）。
- `discover-raw` 用 `--state all`，对已关闭的历史副本也会返回 ok；present 回填的是真实 id，不会新建 open 副本，安全。
- 单机测试里 stub adapter 的 close-multi 恒返回全 closed；真实 0/3/1 分类由 adapter 负责、未改，基线对比已验证。
