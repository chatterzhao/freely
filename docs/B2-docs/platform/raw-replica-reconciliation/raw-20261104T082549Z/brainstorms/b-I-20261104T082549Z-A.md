# Design Brainstorm: I-20261104T082549Z-A

## 决策 1：复用既有 sync-debt 账本，不新建 ledger

`lifecycle/sync-debt.py` 已有 `record/list/clear` 与 `.freely/state/sync-debt.json`，`wt-create` 前置校验也已在 `--allow-degraded` 时用它记账。再建一套会引入「两个账本谁是真源」的漂移。本轮只在 pull 的 partial 分支补一次 `record`。

## 决策 2：pull 只做可用性选择，不重复事实判定

`raw_reconciliation.reconcile()` 已经区分 `unknown`（不确定性 → debt）与 `missing`/`ambiguous`/`diverged`（事实 → block）。`pull_raw_issue()` 属于读通道，职责是「选一个能读的源」；把事实判定搬进来会重复实现且与前置 gate 结论冲突。

## 决策 3：三个循环收窄到 readable，避免伪造身份

`platform_ids` 推导、assignee 认领、title 规范化原本都遍历全部 replicas 并直接取 `i["issue_id"]`。非 ok 副本没有该键，收窄作用域既避免 KeyError，也避免把缺失平台写成空/伪造身份。`_fill_platform_ids` / `issue-sync create` 会在平台恢复后补齐。

## 决策 4：退出码 3 必须在 wt-create 里被当成「继续」

`_pull_raw_issue()` 原来用 `result=$(...) || return 1`。若不改，pull 即使成功物化也会被工位创建拦下，缺陷依旧。因此显式捕获 `pull_rc`，仅 `0` 与 `3` 继续，其余失败。

## 决策 5：stdout 契约不可破

`wt-create` 解析 `result` 为恰好一个 JSON 文档。adapter 输出先落临时文件再 `cat` 转发；所有诊断（assignee、title、partial 警告、issue-sync 结果）走 stderr；sync-debt 记账输出丢弃。测试用 `json.loads(proc.stdout)` 断言。

## 决策 6：显式指定不可读平台 = 失败，不静默回退

用户显式指定读源时，静默换平台会掩盖故障并可能读到不同步的内容。因此 `preferred_platform` 必须命中 `readable`，否则 FATAL。

## 决策 7：不夹带平台写通道

issue 修复方案第 4 条提到「平台写（close/update）同样支持按可用平台执行」，但验收标准 4 条全部只覆盖 pull 链路；写通道是 #4149 的独立 scope，改动会扩散到 `close_issue`/`update_issue`/`close-multi` 多个调用点。本 PR 只交付「部分成功独立退出码 3」（验收标准第 4 条），写通道改造留给 R11。此边界已写入 B1 brainstorms、IDN、GREEN 证据与 review verdict 残余风险。

## 退化审计方法

3 个真源用 `git show HEAD:<file>` 还原到未修改 develop，跑同一套 AT-001 断言得到 RED（9 失败 / 3 既有能力 PASS），再跑 11 个相关回归；恢复新版后同参数复跑。退出码逐一相同（全 0），输出差异仅计时数字。

## 被否决的替代方案

新建独立 sync-debt 账本（双真源漂移）；把 allow_degraded 事实判定搬进 pull（职责重叠）；部分成功仍返回 1 由调用方猜（无法区分硬失败与降级）；把写通道一起改（越界到 #4149）；在 stdout 里打印警告（破坏 wt-create JSON 解析）。
