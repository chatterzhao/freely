# b-I-20261101T031502Z-A: 研究交付的治理载体选择

## 问题

B1 产出对比研究、概念全量对照和三个 `needs_research` 后续方向。要把研究合入 `develop`，需要 I-* 载体；但后续方向的前置动作是行为盘点/度量，不是实现。

## 备选

### Option A: 直接把后续方向之一 promote 成 I-*-A

- 好处：链路最标准，candidate → I-* 一一对应。
- 坏处：会逼出一份尚未验证的 follow-up 或 HarnessPort 设计；pre-tests 无法真实覆盖行为，等于把研究结论伪装成实现设计。

### Option B: 走 doc-only 分支，不绑 raw issue

- 好处：跳过 B1/B2，最快。
- 坏处：raw issue 无法吸收，平台 issue 悬空；研究结论失去 candidate 入口，后续无法从 scan 发现。

### Option C: 把“研究交付”本身登记为 C-A 并 promote 到 I-*-A（选定）

- C-A 的交付物就是研究文档、概念对照、两张图和 candidate 登记；`phase_state` 停在 `in_verification`。
- 后续方向 C-B/C/D 保持 `needs_research`，不被 promote。
- B2 产物按研究交付写：PRD 定义研究范围与验收，pre-tests 验证结构/引用/图/门禁，tasks 记录研究步骤，IDN 记录治理取舍。

## Decision: Option C

- 理由：既不让后续方向伪造 promote，也不让 raw issue 悬空；研究本身有真实、可执行的验收。
- 边界：I-* 不声明 runtime 行为变更；不进入 dev-loop；C-B/C/D 的 `next_action`/`revisit_trigger` 保持有效。
- 风险：C-A 是“研究交付”而非“能力实现”，后续 promote C-B/C/D 需要新 I-*，不能复用本 issue 的完成状态。
