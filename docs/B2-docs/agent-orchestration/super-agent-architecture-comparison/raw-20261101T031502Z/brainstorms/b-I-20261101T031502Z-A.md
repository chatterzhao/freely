# b-I-20261101T031502Z-A: 研究交付的治理载体选择

## 问题

B1 已产出对比研究和两个 `needs_research` candidate。要把研究合入 `develop`，需要一个 I-* 载体；但两个 candidate 都还不该 promote——它们的前置动作是行为盘点/度量，不是实现。

## 备选

### Option A: 直接把 C-A promote 成 I-*-A

- 好处：链路最标准，candidate → I-* 一一对应。
- 坏处：会逼出一份尚未验证的 follow-up 协议设计；B2 的 pre-tests 无法真实覆盖“线程归属”行为，等于把研究结论伪装成实现设计。

### Option B: 走 doc-only 分支，不绑 raw issue

- 好处：跳过 B1/B2，最快。
- 坏处：raw issue 无法吸收，平台 issue 悬空；研究结论失去 candidate 入口，后续无法从 scan 发现。

### Option C: 用 I-* 承载“研究交付”本身（选定）

- I-* 的交付物是研究文档、对比图和 candidate 登记；`phase_state` 停在 `in_verification`。
- 两个 candidate 保持 `needs_research`，不被 promote；I-* 只做 provenance 载体。
- B2 产物按研究交付写：PRD 定义研究范围与验收，pre-tests 验证文档结构/引用/图产物，tasks 记录研究步骤，IDN 记录治理取舍。

## Decision: Option C

- 理由：既不伪造 candidate promote，也不让 raw issue 悬空；研究本身有真实、可执行的验收（结构、引用、图、门禁）。
- 边界：I-* 不声明 runtime 行为变更；不进入 dev-loop；两个 candidate 的 `next_action`/`revisit_trigger` 保持有效。
- 风险：I-* 与 candidate 不是 1:1 promote 关系，后续若 promote C-A，需要新 I-*（同 key 不同 suffix 或新 raw key），不能复用本 issue 的 `completed` 状态。
