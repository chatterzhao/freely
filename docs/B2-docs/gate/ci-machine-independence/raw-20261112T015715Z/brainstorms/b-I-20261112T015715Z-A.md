## 替代实现方案评估

1. **在 `subprocess.run` 外层 `os.environ["PATH"] = ...` 临时改再改回**：
   简单但改全局状态，若断言抛异常会泄漏到后续用例，且并发/复用时难排查。否决。
2. **把 stub 写进沙箱树 `tree/bin/` 并让 `deploy-skills` 自己找**：
   `deploy-skills` 的 `command -v` 只看 PATH，不看仓库内路径，行不通。否决。
3. **改用 `--tools claude,cline` 显式传参绕开 registry**：
   那就完全不测 registry 读取了，等于把被测能力删掉。否决。
4. **自建 stub + `env=` 注入（选定）**：见 PRD M1，改动最小、作用域最干净。

## 边界条件

- `os.environ` 里 `PATH` 可能为空 → 用 `env.get("PATH", "")` 兜底。
- `tmp` 目录在 `registry_checks` 之前已被其它用例使用 → stub 用独立子目录名
  `tool-probe-bin`，不复用 `deploy-tree`。
- registry missing 用例会把 `reg` 改名再改回；stub 不影响这一步，因为
  `deploy-skills` 在 `[[ -f "$_reg_file" ]]` 处就 fail-closed。
- stub 名必须与 registry 中 `cline.test_command` 首词一致；AT 静态断言 S3 守住，
  将来改名要同步（已写入 candidate 的 revisit_trigger）。

## 残留风险

- stub 是「探测用」而非真 cline：它只让 `command -v` 成立，不模拟 CLI 行为。
  本测试的断言只关心「registry 是否被读取」，不执行 cline，故足够。
- 若将来 `deploy-skills` 改用别的 installed 判据（如查配置文件而非 `command -v`），
  stub 会失效 → AT 负向控制与 revisit_trigger 共同守着。
