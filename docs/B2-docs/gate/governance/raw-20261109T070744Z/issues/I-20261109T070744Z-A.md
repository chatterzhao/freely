## 实现

- `governance-merge-gate` 新增 `baseline_text()`：`--staged` 模式取 `HEAD`（合并前的 develop），`--range` 模式取范围左端。
- 新增 `legacy_frontmatter_damaged()`：纯 YAML 判定三类不可解析（glued 闭合 `---`、成对冲突标记、YAML 解析失败），legacy bullet-only 文档不判损坏。刻意不依赖 #4148 的 `parse_issue_text`——本门禁必须先于它进入 develop。
- 新增 `select_repair_only_paths()`：从 `issue_paths` 中挑出基线不可解析的路径。
- 在 `errors`/`warnings` 初始化之后、GATE 1 之前，把这批路径**整体从 owner 集合剔除**并逐条记 warning；后续 phase-vs-code、review-artifact、milestone 归属校验因此不再看到它们。
- 新增 `docs/system/workspace/scripts/tests/test-governance-structural-repair-exemption.py`（AT-001，13 项）。

## 不退化边界

- 基线可解析、key 不匹配的 issue 文档仍然报 GATE 1 error（反向守护，AT-001 有断言）。
- legacy bullet-only 文档（无 YAML 块）不判损坏，不会被豁免。
- 不删任何既有校验；只改变「哪些路径算本次 merge 的 owner」。
- 不改 `pr-merge-guarded`、hook 包装层、`install_state`。

AT-001 develop 基线 RED `5 ok / 8 failed` → 工位 GREEN `13 ok / 0 failed`；真实场景：`raw-20261103T132517Z` 的 PR 在 develop 侧通过合并门禁，28 条错误降为结构性修复 warning。
