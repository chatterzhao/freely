# Design Brainstorm: I-20261106T065711Z-A

## 决策 1：为什么用长驻 `git cat-file --batch` 而不是一次性预读全部路径

`read_repo_text` 的调用路径分散（`parse_issue_file`、`parse_milestones`、`_validate_raw_issue`、`parse_progress_file`、`parse_review_file` 等），且 `canonical_issue_path` 是运行时从文档内容解析出来的，无法预先枚举所有路径。一次性预读会漏路径；长驻进程 + 按 spec 惰性查询 + 进程内缓存既覆盖所有调用点，又保证同一路径只查一次。

## 决策 2：三视图优先级留在 `governance-merge-gate`，不下放到 `RepoView`

用户明确禁止「把 staged/range 视图简化成直读磁盘」。`RepoView` 只负责「把某个 spec 读成文本 / 判断它是否存在」，不决定该读哪个视图；`read_repo_text` 与 `path_exists` 的分支结构逐行保留。这样退化审计可以直接对两版模块逐函数对比。

## 决策 3：非 blob 与无法解析的响应一律回退

`git cat-file --batch` 对 tree/tag/commit、ambiguous spec、坏流会让 header 不是 `<sha> blob <size>`。这些情形下 `RepoView` 抛 `_NonBlobResponse`，由 `exists()` / `read_text()` 回退到原来的 `git cat-file -e` / `git show` 单次调用，边界行为完全不变。真实治理文档全是 blob，回退路径不会被触发，因此不影响性能收益。

## 决策 4：universal newline 与严格 UTF-8 对齐 `text=True`

旧 `git()` 用 `subprocess.check_output(..., text=True)`，会做 `\r\n` → `\n` 转换并以严格 UTF-8 解码。批量读取返回原始字节，若直接 `.decode()` 会在 CRLF 文档上产生差异。因此 `RepoView.read_text()` 显式做同样的转换与严格解码。

## 决策 5：Step 2e 缺扫描器时 fail-closed

旧循环在 `find` 无输出时会静默 `all comments resolved`。若新扫描器因打包/部署缺失，不能退化成「跳过门禁」。因此 `pr-create-guarded` 在文件不存在时打印 ERROR 并置 `_comment_check_failed=1`，走原有失败块。

## 决策 6：性能断言分离算法与环境 I/O

本机 PATH 首位 `brokered-bin` shim 使每次 `python3` 启动 ~3.5s、每次 `open()` ~4.4ms。804 次文件打开合计 3.487s 是环境开销，不是进程扇出。测试因此断言「纯计数 < 1s」+「完整扫描 < 15s 且相对基线 188s 提升 > 50×」，并记录两者数值，避免把环境噪声误判为代码回归。

2. 6 种 CLI 调用模式（3 种 range、range+source-branch、skip-ibm、staged）逐项比对退出码与完整 stdout/stderr。
