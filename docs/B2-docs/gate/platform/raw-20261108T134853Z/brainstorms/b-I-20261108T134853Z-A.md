# Design Brainstorm: I-20261108T134853Z-A

## 决策 1：失败后补救，而不是每次预建

无条件 `gh label create` 会让每条健康建单多 N 次 API 调用。只在 `gh issue create` 明确报「label not found」时才补齐，健康路径零开销。

## 决策 2：错误判定要窄

必须同时含 `not found` 与 `label` 才补救。否则 auth / permission / network 失败会被重试掩盖，甚至被误当成「标签问题」去创建无关标签。这条由行为用例 4 守护。

## 决策 3：重试有界

只重试一次。第二次仍失败就返回原始 error，不循环、不吞错。行为用例 6 守护。

## 决策 4：不改 feedback 层

在 feedback 里 catch 掉错误并「去掉标签重试」会让优先级重新丢失，直接违反 R15 的验收。修复放在平台边界（adapter），语义归位。

## 决策 5：测试用 fake subprocess，不碰真实平台

真机会造 issue。用 `unittest.mock.patch.object(mod.subprocess, "run", fake.run)` 驱动真实 `GitHubHandler`，断言调用序列、次数与返回结构；真机证据由本条 issue 自身的创建过程提供（补标签后双平台 created）。

## 退化审计

1. `git archive develop -- bin docs` 基线快照 + 最终版 AT-001 → RED `6 ok / 8 failed`；
2. 工位同断言 → GREEN `14 ok / 0 failed`；
3. 16 个相关回归（severity / 写通道 / parity / handler-probe / promote / close / install-state / 契约 / 门禁等）与基线逐一对比退出码；
4. 真机：补标签后 `freely feedback create` 双平台 created。

## 被否决

建单后补标签；无条件预建；文档要求人工预建；feedback 层去标签重试。
