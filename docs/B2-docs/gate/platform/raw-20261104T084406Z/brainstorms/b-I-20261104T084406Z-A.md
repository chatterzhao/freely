# Design Brainstorm: I-20261104T084406Z-A

## 决策 1：可选字段而不是必填字段

`validate()` 用 `tuple(keys)` 精确匹配 21 字段。把 severity 变成必填会让 59 份 strict 文档全部失效，并迫使 824 份历史文档批量改写。改为接受两种合法形状（21 / 21+severity 且 severity 在最后），显式创建才追加字段。

## 决策 2：存量回填放在 read view

`normalize()` 与 `_labels()` 都用「显式合法值优先，否则 P2」统一解析。这样「所有 raw 都有合法 severity」在读取与展示层成立，却不产生一次文件写入；副本一致性也不会因本地独有字段被破坏。

## 决策 3：labels 通道要向后兼容

adapter 的 `create_issue()` 被多处调用，handler 也可能是自定义 2 参实现。故只在 `labels` 非空时传第 3 个位置参数；无标签时保持完全相同的 2 参调用。行为测试用一个 Legacy handler 守护这条不退化边界。

## 决策 4：scan 用稳定排序而不是改 find 顺序

`cmd_scan` 原先边遍历边打印。改为收集到数组、加 rank 前缀、`sort -s` 后剥前缀，同级保持原发现顺序；输出行加 `sev=Pn`，让排序结果可核对而不是只能靠猜。

## 决策 5：复用 gate/platform story

B2 文档放进既有 `gate/platform` story，避免新增 story 触发 epics-map 对齐开销（R13 同做法）。

## 退化审计方法

1. `git archive develop -- bin docs` 出基线快照，放入最终版 AT-001 → RED `3 ok / 14 failed`；
2. 工位同断言 → GREEN `30 ok / 0 failed`；
3. 14 个相关回归（写通道 / 关闭路径 / promote / test-gate / wt-close / 契约 / reconciliation / governance 等）与基线逐一对比退出码；
4. 真机：合并后用封装 `freely feedback --severity P0` 验证平台 label 可过滤。

## 被否决

必填 22 字段；批量回填历史文件；只加 label；把 severity 塞进 body；新增 story。
