## 5. 根因是否被修掉

派发面的根因是「四层都没有条件更新 + 抢占发生在启动之后」。本轮把可选前置条件贯通到 DB 单写者的一条 SQL，并把抢占移到启动之前，冲突时 CLI 非零退出让派发循环 `continue`；三处既有 `--expected-status pending` 因此第一次真正生效。SSE 面的根因是「监督者既消费又冒充 pid + 三处检查-写入无互斥」，本轮把监督者降级为只调用唯一启动入口，消费者用 flock 认领 pid，重复 python 实例被 reaped。只做一半都会留下复发路径。

## 6. 范围诚实度

本条**不修** `|| true` 吞错的失败可观测性（#4157/R25）、不重写派发管线、不动启动锁/DB 单实例、不改 watchdog 事件语义；也没有把 SSE 面拆成新 raw（两面同一主题、同一夹具，用户已明确不要无限拆）。一次性路径 `:24789` 仍可直接启动 shell watchdog，但 claim helper 保证它不会成为第二个消费者。

## 7. 残留风险

- 进程 fork 到 pid 文件写入之间有毫秒级窗口；第二个启动者会在 shell watchdog 内被 claim helper 拒绝，不会重复消费，但会短暂存在进程。
- owner 校验依赖 `ps -p <pid> -o command=`；不可用时 fail-closed（拒绝接管），极端情况下需 ensure 循环清理 stale pid。
- A2A Server 未启动时派发循环仍表现为「没有任务」（业务级静默），属 #4157/R25。
- 既有 known-broken 未处理。
