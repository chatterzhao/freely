# b-I-20260717T004654Z-A: 实现设计

## 方案（三点，均在 runtime/freely）
1. **孤儿回收**：`_ensure_acp_bridge_running` reuse 块 fall-through 的 `rm -f "$pid_file" ...` 前：若 `$pid` 非空且存活 → `terminate_pid_with_graceful_wait "$pid" "stale ACP bridge before respawn"`（该函数恒 return 0，set -e 安全）
2. **暖机宽限**：健康检查失败分支：若 pid 存活且 pid 文件龄 <`ACP_BRIDGE_WARMUP_GRACE_SECS`(默认 20s) → log + return 0 复用（冷启动 8s < 20s 覆盖）
3. **lazy 守卫**：主循环 per-cycle ensure：先取 manager base_tool；循环内非 manager 且 `_acp_bridge_pid_file` 不存在的工具 → continue（已被 auto-wake 启动过的工具仍保活）

## 测试映射
AC1/AC2→AT-001（源码断言×2）；AC3→AT-002（源码断言）；AC4→AT-003（E2E wait 100s：spawn 事件≤1、bridge≤1、opencode/cline=0）

## 边界
不改 acp-bridge.py、协议、auto-wake（_sync_project_tooling→_ensure_acp_bridge_running 委派路径不受 lazy 守卫影响——守卫只加在主循环 cycle ensure 块）。

## 实现期新发现（探针实证，churn 真引擎）

**第四缺陷（elif 吞噬 fall-through）**：`elif [[ -n "$running_tool" ]]` 命中后，same-base 情况在内层 if 里"什么都不做"落出整个 elif 链——跳过健康检查直达重生路径。由于 .tool 文件每次 spawn 后必然存在，**每个 cycle 都会拆掉健康 bridge 重生**（探针序列：pidfile_seen alive=1 sock=1 → 直接 reap → respawn，bin/tool/healthy/fail 四分支均未触发）。这是 2026-07-16 泄漏与今日 AT-003 RED 19 次 spawn 的真引擎；孤儿路径（缺陷1）决定了旧进程是否泄漏，本缺陷决定了为什么每轮都重生。
修复：把 base 比较并入 elif 条件（`elif [[ -n "$running_tool" && "${running_tool%%-*}" != "${base_tool:-claude}" ]]`），same-tool 正常流向健康检查。
