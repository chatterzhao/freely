## 1. RED 是否真实

develop `c31b73724` 基线 + 最终版 AT-001 → `5 ok / 8 failed`。

关键两条不是「断言写错」，而是缺陷本体的直接观测：

- `pid file belongs to the surviving daemon ('94129' vs 94128)` —— pid 文件记录的是**已死**进程，存活 daemon 是另一个。这正是 issue 说的「孤儿覆盖 pid / 健康 daemon 的文件被删」。
- loser 输出 `[ERROR] daemon start failed: database is locked` —— 说明当时第二个实例真的起来了，只是被 SQLite 锁碰巧挡住。**没有任何单实例约束**。

TOCTOU 那条同样是真的：基线在「目录刚 mkdir、state.env 未写」时直接回收并抢到锁（`RC=0`）。

5 项 PASS 是既有能力守卫（老目录回收、活 owner 阻塞、cmdline 不可读保守、SQLite 兜底让第二个恰好崩），不是新功能。

## 4. 根因是否被修掉

TOCTOU 的根因是「用目录存在性代替原子性」；本分支没有换原语，而是把**唯一不安全的判定（无 state 就回收）**加上 age 门槛——毫秒级窗口内 age 必然远小于 `stale_secs`，因此不可能误判。

DB 的根因是 check-then-act + 无条件 unlink；本分支用 fork 前的独占 flock 把「判断是否已有实例」和「成为实例」合成一个原子动作，并在 bind 前再做一次正向探测（双保险，因为旧 daemon 可能还在写 socket）。

## 5. 偏离 issue 原文之处（已论证）

issue 写「flock 持有 fd 并继承给 supervisor」。未采纳，理由：①macOS 无 `flock` 命令；②fd 继承会把「启动窗口互斥」变成「运行期独占」，改变 stop/restart 与多实例检测语义，超出本 issue 边界。改为「回收判定进 age + cmdline 校验、DB 用 `fcntl.flock` 只护 pid 文件」，后者正好覆盖 issue 要求的「单实例」。

## 6. 残留风险

- `ps` 不可读时 cmdline 校验退化为保守（会白等超时，但不误杀）。
- 派发仍非幂等（#4239），本轮只堵住「双 supervisor」，worker 重复拉起仍可能——两者独立，已在 IDN 与 goal 记录。
- `/tmp/freely-db-<hash>` 是全局命名，并发跑同一 project 的测试会互扰（本轮用唯一临时项目规避）。

## 结论

RED 是缺陷本体（pid 错位 + 靠 SQLite 兜底），GREEN 覆盖全部验收，未改锁语义、未删既有路径，偏离原文处有明确论证。**verdict: pass**。
