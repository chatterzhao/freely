## Root cause

Commit `805b6d67` introduced hash-based socket/pid paths in `acp-bridge.py` to avoid
AF_UNIX 104-byte limit on macOS, but three other files were not updated to match:

- `monitor-ai-acp.sh`: `_bridge_pid_file()` and `_bridge_socket()` still used old non-hash paths
- `tool-launchers.sh`: hardcoded `${project}/.freely/run/acp-bridge.sock`
- `freely` (bash): `_acp_bridge_pid_file()` and `_acp_bridge_socket()` still returned old paths

Result: ACP bridge listened on hash-based path, but clients looked for non-hash path.
Bridge socket never found → ACP bridge failed to start.

## Fixes

### acp-bridge.py
- `_pid_file()` and `_socket_path()`: use `.freely/run/acp-bridge-{hash}.*` instead of `/tmp/freely-acp-{hash}.*`

### freely (bash)
- `_acp_bridge_pid_file()`, `_acp_bridge_socket()`: add `_acp_bridge_short_hash()`, use hash-based path
- `runtime_pid_file_for_role()`: use hash-based pid path
- `clear_stale_runtime_pid_file_if_invalid()`: use hash-based socket path
- `_ai_shows_liveness_pid_signals()`: use hash-based bridge socket path

### monitor-ai-acp.sh
- Add `_bridge_short_hash()`, update `_bridge_pid_file()` and `_bridge_socket()` to hash-based paths

### tool-launchers.sh
- Replace hardcoded path with `_bridge_socket()` call

## Verification

- daemon start → ACP bridge initializes → socket appears at correct hash-based path
- AI launches via ACP → session/resume → session/prompt → cycle completes in <60s
- AI successfully discovers and executes tasks (temp worktree cleanup verified)
- No ACP bridge socket mismatch errors
