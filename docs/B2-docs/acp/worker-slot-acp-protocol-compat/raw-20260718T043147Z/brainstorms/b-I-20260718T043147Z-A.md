## 问题核心

`acp-bridge.py` 通过 PTY + stdio JSON-RPC 协议与 AI CLI 工具通信。
`opencode acp` 启动的是 HTTP server（监听随机端口），完全忽略 stdin。

两者 I/O 模型不相交 → `initialize` handshake 永远等不到响应 → 30s 超时 → worker 无法启动。

## 修复方案评估

### Option A（已在 B1 选定）：换 worker_slot → claude-apikey-ds-pro-auto

`claude-agent-acp`（claude 家族）使用 stdio JSON-RPC，与 `acp-bridge.py` 完全兼容。
改动：`.freely/agent-table.toml` 中 `worker_slot` 一行。

**实现路径**：
1. 在 worktree 的 `.freely/agent-table.toml` 将 `worker_slot = "opencode-apikey-ds-flash-auto"` 改为 `worker_slot = "claude-apikey-ds-pro-auto"`
2. 重启 daemon（`freely daemon stop && freely daemon start --task-mode auto`）
3. 观察 worker bridge initialize 日志确认成功

**验证链**：
- 配置层：grep agent-table.toml 确认值已更改
- 进程层：worker bridge 启动日志无 ACP timeout 错误
- 业务层：提交一个 test task，观察状态从 submitted → working

**边界**：不修改 acp-bridge.py，不修改 opencode 集成逻辑。opencode 作为 worker tool 的 HTTP ACP 支持留作独立 feature。

## 结论

单行配置改动，无代码风险，可立即验证。
