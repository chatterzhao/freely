## 为何客户端过滤是权威修复

`run-acp-prompt.py` 一个进程 == 一个 client == 一个 session（main 里 `session_id` 在会话协商后唯一确定）。它**确定性地知道自己是 A 还是 B**，因此在 `_handle_message` 入站处比对 `params.sessionId` 是最可靠的判定点。bridge 侧只有「某 socket 引用过哪些 sessionId」的启发式登记（issue 也指出单 bridge 无 session→client 归属），所以 bridge 定向投递只做纵深防御与减噪，绝不作为唯一正确性来源。这也是把「未知 session 丢弃」收窄为「fail-open 广播」的底气：即便 bridge 回退广播，B 的客户端仍会丢弃 A 的消息。

## 为何 positively-mismatched 才丢弃

issue 前置条件 U6：无法保证 `session/update` 总带 `sessionId`。若「无 sessionId 即丢弃」会静默丢消息（退化）。判定表：

| 自身 session_id | 消息 sessionId | 动作 |
|---|---|---|
| 未协商(空) | 任意 | 保留（旧行为） |
| 已协商 | 缺失 | 保留（U6 不丢） |
| 已协商 | 相同 | 保留（本 session） |
| 已协商 | 不同 | **丢弃**（确定的越权） |

仅最后一列产生新行为，其余三列与 develop 逐字节一致。

## 为何不动生产 `bypassPermissions`

它是**服务端** `session/set_mode` 的 modeId，非 client `--mode`。生产由 `monitor-ai-acp.sh`→`_load_slot_env_vars` 从 settings.json 注入 `CLAUDE_CODE_PERMISSION_MODE`（模板值 `bypassPermissions`）。直接翻裸默认会让未配置部署需审批而可能 hang。方案：保留该 env 权威 + 加 `FREELY_ACP_BYPASS_PERMISSIONS=1` 逃生开关 + 仅裸默认改 `default`。「默认路径下权限请求必须 session 匹配」由客户端权限守卫满足（实质安全目标），而非靠改 modeId。
